# Скилл `mr-review` — дизайн

Дата: 2026-10-16
Статус: черновик на согласование

## Зачем

Сейчас при каждом ревью MR агенту руками задаются три вещи: **какой MR**,
**насколько глубоко** проверять и **на что смотреть**. Из-за этого ревью у всех
в команде разное и каждый раз требует вводной.

Цель — **единый стандарт ревью внутри команды**, запускаемый одной командой
без описания контекста. Скилл публичный: им могут пользоваться и другие команды,
поэтому конкретный стек в нём не зашит — правила команды лежат в репозитории.

Успех выглядит так: разработчик пишет `/mr-review 123 hard` и получает
структурированный отчёт по одному и тому же стандарту, что и коллеги, ничего
не объясняя.

## Цели

- Одна команда вместо ручного задания параметров.
- Три режима глубины: `standard`, `hard`, `ultra`, каждый со своими
  зонами проверки «из коробки».
- Прогон существующих тестов и сборки на ветке MR как часть ревью.
- Единый формат отчёта и единая шкала серьёзности.
- Поддержка GitLab (MR) и GitHub (PR).
- Работа в любом агенте, где есть субагенты (Claude Code, Codex, Cursor и т.п.).
- Командные правила — из файла в репозитории, а не из промпта.

## Не-цели

- Агент **не пишет** тесты и не чинит код. Недостающие тесты — это замечание к MR.
- Не апрувит и не мёржит MR.
- Интеграция с трекером задач — отдельный будущий скилл (единый стиль описания
  задач). В этом скилле её нет; можно оставить точку расширения.

## Анти-цели (провал, даже если «работает»)

- Комментарии уходят в MR **без явного подтверждения** пользователя.
- Ревью требует каждый раз объяснять контекст — значит, стандарт не сработал.
- Шум: десятки мелочей, за которыми тонут реальные блокеры.
- Скилл портит рабочее дерево пользователя (переключает ветку, оставляет мусор).
- Скилл привязан к одному агенту или к конкретному стеку.

## Запуск

```
/mr-review [MR] [standard|hard|ultra] [--focus <область>]
```

- **MR** — номер или ссылка. Если не указан — MR/PR текущей ветки.
  Если MR для ветки нет — ревьюится **локальная ветка** против базовой
  (`main`/`master` или указанной), без шага публикации. Этот же путь
  используется для проверки самого скилла.
- Скилл работает внутри локального клона репозитория MR. Ссылка на MR из
  другого репозитория → сказать, что нужно перейти в его клон; самому не клонировать.
- **Режим** — если не указан, агент оценивает размер и характер диффа и
  **предлагает** режим, но не запускает `hard`/`ultra` без согласия.
- **`--focus`** — опционально сужает/акцентирует проверку (например `security`).
  По умолчанию не нужен: зоны заданы режимом.

### Определение платформы

По remote текущего репозитория: GitHub → `gh`, GitLab → `glab`. Если CLI не
установлен или не авторизован — сказать, что именно сделать, и остановиться.
Если хост не распознан (self-hosted) — спросить один раз.

## Командные правила: `REVIEW.md`

Опциональный файл в корне репозитория. Скилл читает его перед ревью и
передаёт всем субагентам. Содержимое (точный формат — на усмотрение
исполнителя, но в скилле нужен шаблон):

- стек и конвенции команды;
- что считать блокером в этом проекте (дополнительно к общему правилу);
- команды тестов и сборки;
- язык комментариев в MR (по умолчанию — язык, на котором общается пользователь);
- пути/файлы, которые не ревьюить (сгенерированное, lock-файлы).

Если `REVIEW.md` нет — скилл работает на общих правилах и в конце отчёта
одной строкой предлагает создать файл по шаблону.

## Тесты и сборка

- Запускаются **существующие** тесты и сборка на коде ветки MR.
- Команды: из `REVIEW.md`, иначе определяются по проекту (`package.json`,
  `Makefile`, `pyproject.toml`, `go.mod` и т.п.). Если определить нельзя —
  сказать об этом в отчёте, не гадать.
- Изменённая логика без тестов → обычное замечание (🟡).
- Рабочее дерево пользователя не трогается: код MR берётся в отдельный
  временный worktree, который удаляется после прогона.
- **Зависимости:** в worktree ставятся заново пакетным менеджером проекта
  в «замороженном» режиме (не меняя lock-файл), например `bun install --frozen-lockfile`.
- **Доверие к коду** (решение пользователя): MR из того же репозитория —
  установка и прогон автоматически. MR из **форка** — агент сначала показывает
  команды, которые выполнит, и ждёт подтверждения. Отказ → тесты помечаются
  «не запускались», ревью кода продолжается.
- **Как трактовать падения:**
  - Упавший тест или сборка → агент прогоняет **то же самое на целевой ветке**.
    Падает и там → «падало до MR», не блокер, отдельная строка в отчёте.
    Падает только на ветке MR → 🔴 блокер с выводом ошибки.
  - Падение из-за окружения (нет БД, Redis, env-секретов, сети) → «не удалось
    проверить» с причиной, не блокер. Команды для такого окружения можно
    описать в `REVIEW.md`.

## Шкала серьёзности

| Уровень | Значение |
|---|---|
| 🔴 Блокер | Ломает логику или поведение; тесты/сборка, упавшие из-за MR; плюс критерии из `REVIEW.md` |
| 🟡 Стоит поправить | Структура, читаемость, отсутствие тестов, нарушение конвенций |
| ⚪ Мелочь | Стиль, вкусовщина, необязательные улучшения |

Каждое замечание (и в отчёте, и в комментарии к MR — решение пользователя):
- уровень, файл:строка, суть;
- **почему это проблема** — конкретный сценарий, что сломается/ухудшится;
- **почему такая серьёзность** — какое правило шкалы сработало; в `ultra` —
  выжимка аргументов спора (без пометки «спорно» в комментарии);
- **варианты исправления** — 1–3 варианта с компромиссом каждого, первый —
  рекомендуемый.

## Режимы

### `standard`

- Для небольших изменений, не трогающих логику.
- Один агент, субагенты не нужны (работает и в агентах без них).
- Проходит весь дифф, запускает тесты/сборку, пишет отчёт.
- Если видит, что MR всё-таки трогает логику, — не отказывается, но в начале
  отчёта пишет: «MR меняет логику, рекомендую `hard`».

### `hard`

- Три субагента параллельно, каждый со своей зоной:
  1. логика и корректность;
  2. архитектура и структура;
  3. тесты и безопасность (включая прогон тестов/сборки).
- Главный агент сливает дубли и собирает одно общее саммари. Спора нет.

### `ultra`

- Пять субагентов параллельно: корректность, архитектура, безопасность,
  производительность, тесты (включая прогон).
- Перед спором главный агент сливает дубли (одно и то же замечание от разных
  ролей → одно замечание).
- **Раунд спора:** все пять агентов голосуют по каждому замечанию (автор тоже —
  его исходная оценка считается голосом): 🔴 / 🟡 / ⚪ / «не проблема»,
  с одной строкой обоснования. Раунд один, без повторных итераций.
- Итоговая серьёзность — **по большинству**. Технически: голоса упорядочены
  «не проблема» < ⚪ < 🟡 < 🔴, берётся **медиана** пяти голосов. Если за
  какой-то вариант ≥3 голосов, медиана совпадает с ним; при раскладе вроде
  2/2/1 медиана даёт однозначный ответ без отдельного правила ничьей.
- Если голосование **не единогласное**, у замечания в терминале ставится
  пометка «серьёзность спорная» с раскладом голосов. **В комментарий к MR
  пометка не идёт** — туда уходит только итоговый уровень.
- Если большинство решило «не проблема» — замечание не публикуется; в
  терминале оно показывается в свёрнутом списке «отклонено в споре».

## Отчёт и публикация

1. Отчёт **всегда** выводится в терминал: вердикт, результаты тестов/сборки,
   замечания по уровням (блокеры первыми), в `ultra` — пометки спора.
2. Затем агент спрашивает, публиковать ли в MR. Ответ: «все», номера
   замечаний через запятую или «нет». По умолчанию в «все» входят 🔴 и 🟡;
   ⚪ публикуются, только если выбраны явно (против шума).
3. Только после подтверждения — публикация **инлайн-комментариями к строкам**
   через `gh`/`glab`. На GitHub — одним review со статусом «comment»
   (не approve / request changes). Замечания без привязки к строке или на
   строках вне диффа — одним общим комментарием.
4. **Повторный запуск** на том же MR: каждый комментарий скилла несёт скрытую
   метку (HTML-комментарий с id замечания). Перед публикацией скилл читает
   существующие комментарии и не дублирует уже опубликованные.

## Переносимость

- Формат — стандартный `SKILL.md` (Agent Skills), без привязки к API
  конкретного агента. Инструкции формулируются как «запусти субагента с
  таким заданием», а не через имена инструментов одного агента.
- Промпты ролей субагентов — отдельные файлы рядом со `SKILL.md`, чтобы
  основной файл оставался коротким и роли можно было править независимо.
- Если субагентов нет, `hard`/`ultra` честно сообщают об этом и предлагают
  `standard` (не эмулируют роли последовательно молча).

## Проверка скилла

Скилл проверяется на поведение, а не на «файл существует»:
фикстуры — маленький репозиторий с веткой, в которую заложены проблемы
(сломанная логика, отсутствующий тест, косметика, упавший тест). Прогон
через режим локальной ветки, без реальных MR. Сценарии: каждый режим находит
блокер, `standard` на логической ветке рекомендует `hard`, тест, падавший и на
базовой ветке, не становится блокером, рабочее дерево остаётся чистым.
Публикация без подтверждения проверяется отдельно на тестовом PR в
песочнице-репозитории.

Обязательная проверка — в Claude Code. Остальные агенты с субагентами — по
возможности; формат инструкций должен это не исключать.

## Решения автора дизайна (не обсуждались с пользователем)

Приняты при подготовке документа, пользователь может их пересмотреть:

- тесты в отдельном временном worktree, зависимости — frozen-установка;
- сравнение падений с целевой веткой; падения из-за окружения — не блокер;
- в `ultra` голосует и автор замечания, итог — медиана пяти голосов, раунд один;
- ⚪ по умолчанию не публикуются; выбор замечаний по номерам;
- GitHub — один review со статусом «comment»; защита от дублей при повторном запуске;
- без MR — ревью локальной ветки; MR из чужого репозитория не клонируется;
- без субагентов `hard`/`ultra` не эмулируются, предлагается `standard`;
- обязательная проверка — только в Claude Code.

## На усмотрение исполнителя

- Точная структура папок и имена файлов ролей.
- Точный формат и шаблон `REVIEW.md`.
- Эвристика выбора режима по диффу.
- Формулировки промптов ролей и формат вывода субагентов.
- Упаковка (например, как Claude Code plugin) и README для публикации.
